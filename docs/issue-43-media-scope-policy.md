# Issue #43 — メディア保護の対象範囲とstrict運用契約

2026-10-30、PR #69で最小限のポリシーを確定する。対象はPR #65に
統合されるWordPressメディア保護であり、サイト全体のファイル保護製品ではない。

## 対象範囲

- **対象**：WordPressのattachment投稿として登録された原本と、
  WordPressの正本メタデータ（_wp_attached_file /
  _wp_attachment_metadata）で帰属確認できる派生ファイル。
  サムネイルが独立したattachment投稿を持たなくても原本の保護を引き継ぐ。
- **保証対象外**：FTP/SSH/他アプリから置かれ、WordPressの添付データに
  帰属しないファイル。CDN・他プラグインの独自ストレージ、
  Rewriteを通過しない配信経路、WordPressのメタデータAPIを経由しない
  直接SQL/ファイル操作も保証範囲に含めない。
- 管理外ファイルの自動収集、例外登録UI、移行専用DB、
  ディレクトリ全体の許可設定は**実装しない**。
- **「保証対象外」＝「strictで自動公開」ではない。**
  索引のunresolvedだけでは、管理外ファイルと登録済み添付の索引欠落を
  区別できない。公開許可の根拠がないファイルは公開しない。

## 動作契約

メディア保護設定ONで、uploads対象拡張子・Rewrite経由の
WordPress PHP配信に入ることが前提。

**次の表は一般閲覧者（ESPの保護パス認証を持たない利用者、
かつWordPressのupload_files権限を持たない利用者）を対象とする。**
現行実装では、ファイルパス検証とメディア保護ON確認の後、
索引・保護パス照会よりも先に、WordPressの is_admin() コンテキスト
**または** current_user_can('upload_files') を満たすリクエストを
特権配信（no-store）へ進める既存例外がある。これはESP独自の
保護パスワードを要求しない。upload_files はWordPress管理者だけでなく
Author等にも付与され得るため、**全ログインユーザーを特権扱いしない**。
is_admin() はWordPress管理側リクエストの文脈判定であり、
認証済み・manage_options保有を意味しない。この既存例外を
今回の文書化で新設・拡張したわけではない。

| 判定 | 互換モード（索引opt-in OFF） | strictモード（索引opt-in ON） |
|---|---|---|
| 正常に帰属確認、保護IDあり | 認証要求 | 認証要求 |
| 正常に帰属確認、保護IDなし | 公開 | 公開 |
| 管理外のファイル／帰属不明 | Resolverで未解決なら公開 | **403**（索引欠落と区別不能） |
| 複数の競合する所有者 | 安全側で拒否 | **403** |
| 索引dirty、索引DB失敗、索引未READY | **索引状態を参照せず、従来Resolverで認可を継続**。従来Resolver自身のエラー・曖昧一致では拒否 | **503などで拒否**、旧方式へ戻さない |
| 消滅した保護パスID | 拒否 | **403** |

※ 互換モードではESP_Media_Index::resolve()を呼ばないため、台帳dirty・未READY
という理由のみで保護ファイルを拒否しない。従来Resolverが正常に所有者と
保護設定を確定できる場合は、公開／パスワード要求を続ける。

※ 互換モードの「未解決を公開」は既存サイト向けの互換動作であり、
管理外ファイルの安全性を検証したことを意味しない。
実際のメタデータ異常ではResolverがエラーを返して拒否する場合もある。
管理者がメディア保護自体をOFFにした公開動作は別契約。

## 有効化と移行

- 初期状態は**索引opt-in OFF**。台帳READYのみでstrictを自動有効化しない。
- strictを使用する場合、WordPress登録済み原本・派生を索引READYにし、
  管理者が影響を確認して明示的に選択する。未登録URLはstrict配信経路で403。
- 管理外ファイルを提供する必要があるサイトでは、管理者がWordPressの
  メディアライブラリへ正式に取り込むか、ESP管理対象外の別配信を設計する。
  当該配信経路のRewriteとアクセス制御はサイト管理者の責任。
- strict有効化後にDB障害・dirty・索引異常が起きても互換方式へ自動退避しない。
- 認証済み保護メディアは共有キャッシュ保存禁止。HEAD/Range/ログアウトも確認。
- 直接URLの配信制御にはApache Rewriteが必要。LiteSpeed/Nginx/CDNなどの
  未検証環境まで保証しているとは表明しない。

## CI検証

1. 互換モードで登録済み保護JPEGは未認証拒否。管理外の無登録JPEGは従来どおり公開。
2. CI専用DBで明示的にstrictへ切り替えると無登録JPEGは403、
   登録済みの原本・派生は認証状態に従う。
3. 登録済み保護派生の索引行欠損では403、dirtyでは503。
   WordPress正本から復旧すると認証要求に戻る。
4. ログイン・ログアウト、公開JPEG、Range、HEAD、保護メディアのno-storeは
   既存の実HTTP回帰で検証する。
5. strict下でWordPress Author（upload_filesあり）の既存特権配信、
   Subscriber（upload_filesなし）および匿名利用者の保護要求を
   実HTTPで照合する。WordPress権限とESPの保護パス認証は別物。

**Q01（#67）は対象外**。wpdbの再送によるpending_count二重減算は既知の
未解決問題であり、今回の適用範囲明確化では解決しない。
