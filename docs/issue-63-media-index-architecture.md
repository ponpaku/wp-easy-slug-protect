# Issue #63 — 専用メディア帰属・保護索引（段階的導入）

## 目的とデータ契約

WordPressの正本を `_wp_attached_file`・`_wp_attachment_metadata`・
`_esp_media_protected_path_id` とする。ESPの専用索引は派生データであり、
保護設定の正本として扱わない。WordPressが管理する添付の元ファイルと
現在の派生ファイルを uploads 相対パスで列挙し、**公開画像も含めて登録**する。

- `{prefix}esp_media_files_v1`：パス SHA-256、相対パス、添付ID、保護パスID。
  `(path_hash, attachment_id, generation)` を複合主キーとし、複数所有者は複数行で保持。
  候補行のパスをPHPの `hash_equals()` で完全一致確認。
- `{prefix}esp_media_file_state_v1`：添付単位の `dirty/ready`、
  `pending_count`、`revision`、`active_generation`、更新時刻、
  `retry_after`・`failure_count`。添付ID `0` を予約した制御行のみ
  `status`を全体READY、`revision`を監査世代、`audit_cursor`を監査位置に使う。
  更新中の旧世代・新世代のどちらも公開判断に使わない。
- `resolve()`：`resolved(attachment_id, protected_path_id)`／
  `unresolved`／`ambiguous`／`error`。
  `unresolved` は公開可能と同義ではない。
- `ESP_Media_Protection::handle_media_access()`：厳格モード時のみ索引を利用。
  `unresolved/ambiguous` は403、`error`は503。解決成功時は最新の
  ESPパス設定と認証情報を確認する。ユーザーにより許可が変わる
  メディアレスポンスを共有キャッシュしてはならない。
  なお、通常PHP配信では専用索引を検索する**同じSQL文**でWordPressの
  保護メタをLEFT JOINし、コピー済み保護IDと不一致・重複なら503として拒否する。
  さらに同一SQL内の全体制御行が `ready` であることも照合する。
  （DBへの往復は1回。索引行やWordPressのREADYオプションキャッシュだけを
  権限の絶対的正本にはしない。）
- 高速ゲート #37 は索引クラスをHTTPから呼ばない。別途生成・検証する
  認可スナップショットの設計が必要。現段階でゲート自体は変更しない。

## 更新・失効の範囲

WordPress標準postmetaフックの**変更前**に添付単位の `dirty` と
`pending_count` を保存する。フックの第5引数は操作ごとに異なるため、
add/update/deleteのガードを分離する。失効のDB書込みが失敗した場合は
互換モードでも全体 `READY=0` を実DBから確認できない限り元の操作を拒否する。
削除開始時に失効できず全体失効も失敗した場合は削除を例外で停止する。

**メタ更新フックから独自のSTART/COMMIT/ROLLBACKを実行しない。**
呼び出し元に既存のMySQLトランザクションがある場合、`dirty`・メタ更新・
`pending_count` の変更は同じトランザクションに参加する。ROLLBACKで
一緒に戻り、COMMITで一緒に可視化される。WordPress Coreは1回の更新で
同じキーの複数行分の更新後フックを発火し得るため、**更新後フックからは
pendingを減算しない**。事前フックで取得したローカルチケットを
WordPress `shutdown`の最終優先度と後続PHP shutdownコールバックで
リクエスト末尾に完了する（PR #70/F01）。
SQL減算が成功した場合にのみローカルの完了追跡を消し、
他更新のpendingがまだ残っていることと、今回の減算失敗を区別する。
DB接続喪失など結果不明の書込みには二重減算の危険があるため、
自動的に `pending=0` に補正せず、長期残存は診断対象とする。

**新規所有パスの事前予約**：`_wp_attached_file`／`_wp_attachment_metadata`
の更新前に、提案された正本からファイルパスを列挙し、添付のdirty化の後に
同じファイル索引へ未確定世代の所有者行を挿入する。
既存の公開所有者と競合すると、そのパスは再構築完了までエラーになる。
WordPressの呼出元にトランザクションがあれば正本と予約行は同じCOMMITに参加する。
予約不能な更新は厳格モードでは拒否する。互換モードで許可する場合は、
先に全体READYを取り消して監査世代を進める。
ファイル列挙は#42に合わせ、トップレベル`file`のない非PDFの
派生`sizes`から所有関係を確定しない。PDFのみ既存の例外を認める。

**投稿種別変更の所有者フェンス（R01）**：通常投稿などが
`wp_update_post()`により`attachment`へ昇格すると、既存メタデータを
そのまま新しい所有者として持ち込める。この更新では`add_attachment`も
メタデータガードも呼ばれないため、`pre_post_update`で投稿種別の
出入りを検出し、Coreによる`wp_posts`更新**前**に対象投稿IDの
`dirty,pending>0`を確保する。昇格時は既存WordPress正本メタデータを
直接読み直し、候補となるファイルパスを未確定世代に**先行予約**する。
新所有者がまだ通常投稿の間もそのパスの照合は安全側で拒否し、
公開済みの他ファイルへの配信は継続できる。
メタデータの欠落・重複・不正・予約失敗時はstrictモードで投稿種別変更自体を
例外で止める。互換モードでは予約失敗時に全体失効へフォールバックする。
投稿種別変更の事前ガードと孤立行回収は**同じ添付IDの名前付きDBロック**を使い、
正本更新前にチケット確保とパス予約を直列化する。既存トランザクションの
未コミット行に対しても孤立回収側の`INSERT IGNORE`／pending条件付き更新が
確定まで待ち、予約行を消す競合を避ける。
Cronの孤立行回収は`pending>0`の移行チケットを削除せず、
既にREADYなら全体監査末尾でも**未完了の移行中投稿を理由に全体READYを取り消さない**。
WordPress更新後にリクエスト末尾でpendingを完了し、
Cronの通常dirtyキューが対象添付を再構築する。これにより、
1件の変更で全件200添付ずつの再監査完了まで全体を503にする負荷を避ける。
外部トランザクション中は正本更新・dirty化・予約が同じトランザクションに参加する。
DB応答消失・異常終了後のチケット復旧は引き続きIssue #67の対象であり、
この対応によって解消したとは扱わない。

**実HTTP性能の測定境界（R02）**：所有者照合SQLが1往復であることと、
WordPressのHTTPリクエスト全体が1往復であることは異なる。
独立Apacheリクエストで`SELECT VERSION()`、非autoloadオプション取得、
所有者照合SQLの回数を別々に記録する。PHP内の温まった40回ループの
ベンチマークはlookup単体の比較として扱い、実HTTP全体の費用には外挿しない。

独立Cronワーカーが、コミット済み `dirty, pending=0` を優先して処理する。
再構築は1添付につき名前付きDBロックで直列化し、次を実施する。

1. 元の索引行を**残したまま**状態を `dirty` にし、`revision` を進める。
2. WordPress正本を再読込して、新しい世代のファイル行を段階的に挿入する。
3. 同じrevision・pending=0なら、単一UPDATEで
   `active_generation=revision, status=ready`を公開する（CAS）。
4. その後に旧世代を削除する。削除失敗は容量面だけの問題で、旧世代は
   ready検索で無視される。

この順序なら、再構築中に古い保護済み所有者が消え、同じパスの
公開所有者が一時的に唯一の候補になる不具合を防げる。
ステージング途中でSQLエラー・PHP終了が起きても状態はdirtyのままであり、
次のワーカーが世代を進めて再試行する。
ただし名前付きロックは権限・接続の制約があり、同時接続・障害時テストが必要。

**保証範囲の制限：** WordPressフックを通過するメタデータ変更が対象。
直接SQL/FTP/外部配信/CDNは変更前失効を保証しない。フック外の変更に
対して定期Cronは将来の修復に役立つが、更新直後の未認証配信を防ぐ
機構の代用にはならない。また、要求時のチェックと実配信の間の
競合・瞬間的な認証失効を完全に排除するものではない。

実装側で失敗・破損を検知できることと、あらゆる更新方法を含めた
完全な即時整合性を保証することを混同しない。

## Cronバッチ

`esp_media_index_v1_batch` を5分間隔で予約。索引操作はHTTP経路とは分離する。

- **削除済み添付の回収**：状態表の孤立行は各Cronで最大200件検出し、
  状態行なしのファイル行は全件監査サイクルの終わりに最大200所有者を処理する
  （大規模なファイル索引を5分ごとに全走査しないため）。
  対象の状態を先に`dirty`にし、ファイル行を消してから状態行を消す。
  回収が残る場合はREADYを新たに公開しない。途中失敗時も配信を許可しない。
- **優先キュー**：`dirty,pending=0,retry_after<=現在時刻`の添付を最大200件処理。
  メタデータ不正など添付単位の失敗は`failure_count`と`retry_after`を記録し、
  次回を1～60分後に延期する。異常を放置したまま`ready`には戻さない。
- **全件監査**：続けて最大200添付を順番に照合する。失敗した添付を飛ばして
  カーソルを進めるため、不正添付1件が全メディアの更新を塞がない。
  通常のWordPressメタ更新では再試行時刻・失敗回数をリセットする。
- **全体READYの判定**：全件監査サイクル末尾に限り確認する。
  初期構築・障害による全体失効から`READY=1`へ戻すには、すべての
  添付の状態が`ready`、未完了pendingがなく、削除済み添付の状態行と
  状態行なしのファイル行が残っていないことが必要。
  すでに`READY=1`であれば、個別添付の`dirty`は**その添付だけ503**とし、
  正常な添付は配信可能に保つ。所有者不足・孤立状態など全体の帰属範囲が
  不明な場合に限りREADYを取り消す。schema v1/v2→v3移行でも
  全体失効・再監査を行う。
- **監査世代のCAS**：全体失効時に制御行の`revision`を進め
  `audit_cursor=0, status=dirty`にする。Cronは読み取った世代・カーソルに
  一致する場合のみカーソルを前進／READYを公開できる。
  途中で別接続が全体失効した場合、古いCronのCASは成立しない。

個別のデータエラーは他の添付と切り離し、DB全体の障害や孤立行の回収失敗では
バッチを中断する。長時間残るpendingは自動的に公開せず、管理者の点検を要する。
初期化・バックフィルのSQLは配信リクエスト中に実行しない。
CronはWP-Cronなので、サイトのアクセス状況によって実行が遅延する。
数十万件規模ではサーバーCronによるWP-Cronの駆動を推奨する。

## 既存サイトでの導入

**自動で新方式に切り替えない。** 既存の未登録ファイルや第三者が生成する
メディアは、厳格モードで403になる可能性があるため、#43の管理外
ファイルの棚卸しと明示例外のポリシーを先に確定する。

管理者が十分な動作確認を行ったあと、次を検証する。

```bash
wp option get esp_media_index_v1_schema
wp option get esp_media_index_v1_ready
wp option get esp_media_index_v1_cursor
```

`schema=3, ready=1` は**初期照合を完了したこと**を意味し、
現在のDB・uploadsの任意変更まで完全に追跡できている証明ではない。

ステージングで厳格モードと既存URLの回帰検証を行う場合：

```bash
wp option update esp_media_index_v1_enabled 1
# 不具合・移行前サイトでは元の配信経路へ戻す：
wp option update esp_media_index_v1_enabled 0
```

ただし互換モードを選んだ場合、PR #62の `unresolved→通常配信` という
既知の#43未解決リスクが残る。戻したから保護が安全になるわけではない。
新テーブルは無効化後も残し、アンインストール時の削除は
データ移行・復旧手順を決めた段階で別途設計する。

## 初期構築時間の実測（2026-10-29）

先に提案した「小規模2,000添付／大規模10,000添付」「CLI 20添付/秒」
「10万添付のCLI構築1〜3時間」は実測に基づく基準でなかったため**撤回**。
規模区分の確定には初期構築を何時間まで許容するかという運用要件が必要。

- 測定対象：実際の `ESP_Media_Index::run_batch()` と `reindex_attachment()`。
  WordPress post/postmetaは合成、MySQL 8.0の実表へ5パス/添付を登録。
  200添付ごとの監査カーソル更新・世代公開・500Kファイル行・最終READYを検証。
  PHP 8.3.36、MySQL 8.0.46、GitHub Actions ubuntu-latest＋MySQLサービス。
- [10K測定 run #40802598029](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/40802598029)：
  1K 5.799s、5K 28.350s、10K **56.760s（176.18添付/秒）**。
- [100K測定 run #40803014462](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/40803014462)：
  1K 4.601s、5K 22.381s、10K 45.459s、50K 230.769s、
  **100K 470.383s（7分50.4秒、212.593添付/秒）**。
  ファイル行500,000、200件バッチp95 1.001s、READY確認成功。
  合成データ生成2.597sは構築時間に含まない。
  10K値が別実行では45.459sと56.760sで異なり、同じCIでも変動する。
- 未測定：完全なWordPress／WP-CLI起動、Apache HTTP、同時更新・本番負荷、
  遠隔MySQL RTT、複数サーバー、障害再試行。7分50秒は本番サイトの保証値ではない。
  ベンチは通常PRで10K、手動workflow_dispatchで100Kを選べる。

現行Cronの定常的な時間換算は `ceil(N/200)*5分`。
N=100Kで41時間40分。初回実行時刻・WP-Cron遅延・最終確認を除く。
30分・1時間・2時間・4時間を許容すると仮定した場合の境界値は
1,200・2,400・4,800・9,600添付。ただし、その許容時間は製品SLOの判断であり、
計測だけから客観的に決めることはできない。

次段階：実WordPress＋WP-CLI、遠隔DB・並行負荷での再測定、
負荷制限・停止再開の受け入れ条件、正常添付まで毎回再構築する全件監査の見直し。
