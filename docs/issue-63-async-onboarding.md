# Issue #63 非同期メディア保護台帳構築 — PR #66 作業設計

> 2026-10-29。PR #65の**作業ブランチ**であり、PR #65 / PR #62 / main の既存ブランチは変更しない。
> PR #66 は Draft。PR #65に取り込み、全体レビュー・CI後にmainへ、実機検証後にリリース。

## 利用者に対する契約

- 新規インストールと更新を区別しない。WordPressの導入処理で全件バックフィルを同期実行しない。
- メディア保護台帳が未完成なら「現在、メディアは簡易的な保護状態」と管理者に継続警告し、
  設定ページから速やかな構築実行を求める。ユーザー操作を待たずにWP-Cronが進める。
- 管理画面から手動で順次構築・再開・手動停止できる。画面を閉じてもCronは継続する。
- 大規模サイトにはWP-CLIを案内する。閾値は現時点で確定しておらず、完了時間SLOが必要。
- テーブル構築完了はただちにstrictモードへの自動移行を意味しない。
  Issue #43の管理外ファイル移行ポリシーと認可回帰を通過した場合のみ切替可能とする。
- 一度strictへ切り替わった後は、障害を理由に旧方式へ自動で戻さない。

## 実装済み（このブランチ）

1. `ESP_Media_Index::register()`: 共通エンジンに対して、Cron、nonce付き管理AJAX、
   WP-CLI `wp esp media-index build` / `status` を接続。
2. `ESP_Media_Index::ensure_schema_on_admin()`: 管理者の最初の正常な管理画面で、
   未作成の空スキーマを準備。CronやCLI側も既存の`run_batch()`から作成できる。
3. `ESP_Media_Index::build_status()`: 全体READY（SQL制御行と互換オプション）、
   添付件数、カーソル、走査済み件数、dirty件数、最終処理時刻を読み取る。
4. `run_batch()`: 既存の世代・CAS・pending管理を保持しながら、
   scan単位のMySQL名前付きロックを導入。複数実行元が同時にカーソルを進めない。
5. `verify_ready_attachment()`: 正常なready添付はWordPressの正本メタデータと
   **現物のactive-generationファイル行**を照合。正しい場合は書込みゼロ。
   欠損・保護ID改変・余分な行・メタデータ不一致時は既存`reindex_attachment()`へ渡し、
   まずdirtyでフェンスしてから再構築する。
6. 管理画面の未完成警告、設定画面の手動構築・進捗・手動停止・CLIの案内。
   手動停止はブラウザーの連続実行を止めるだけで、Cronは止まらない。
7. MySQLの欠損行・保護ID改変修復・正常行無書込み・別接続scan lock試験を追加。

## 状態と安全境界

| 内部条件 | 保護方式 | 操作 |
|---|---|---|
| 台帳スキーマ未完成、索引opt-in OFF | 既存の互換保護。派生ファイル保護漏れという既知制約あり | エラー判定、Cron・管理構築を継続 |
| 台帳構築中、索引opt-in OFF | 同上（簡易保護）。管理者へ常時警告 | Cron・手動・CLIを共用 |
| 全体READY、索引opt-in OFF | 同上 | Issue #43の移行判定・レビュー待ち |
| 索引opt-in ONでREADY | 台帳に基づく厳密判定 | dirty/不明は拒否 |
| 索引opt-in ONで未READY/DB障害 | **503等のfail-closed**。自動で簡易保護へ戻さない | 修復・診断 |

WordPressのランタイムREADYと台帳READYは別状態であり、同じ意味にしない。

## 2026-10-29 PR #65 読取りレビュー R01–R03 への対応

元レビューは PR #65 の `78d492df` を対象としており、下記修正は
**派生PR #66のみ**に含まれる。PR #65の旧HEADで解決済みと表現しないこと。

- **R01 異なる年月ディレクトリへの移動**：
  **2026-10-29追加レビューで方針変更**。段階的なディレクトリ移動は
  WordPress Coreの標準操作ではなく、プラグインの原子的移動保証の対象外。
  移動先の派生ファイルを推測して部分予約する旧処理は削除。
  `_wp_attached_file` と `_wp_attachment_metadata.file` の
  ディレクトリ不一致をWordPress APIフックで検出した場合、
  **全体の索引認可を確実に失効させてからメタデータ書込みを許可**する。
  全体失効できなければ書込みを認めない。メタデータが揃うまでは
  Cronは再構築を完了できずdirty・再試行のままにする。
  正本が整えば既存Cronだけで索引を再構築・全体READYを復旧する。
  管理画面に再構築待ちの警告と確認先を表示する。
  APIフックより先に実ファイルが動いた場合やFTP/SQL直変更は保証外。
  **異常検出後のfail-closed**と**実体移動前の安全保証**は混同しない。
- **R02 後から登録されたPHP shutdown callbackでのno-op**：
  メタ更新のpre-hookでlocal pendingを取得する時点で、後続PHP shutdown
  finalizerを動的に登録する。shutdown中に新たなpre-hookが呼ばれた場合も
  キュー末尾に追記し、後続callbackより後に自分のpendingを回収する。
  実WordPressのPHP終了時の連鎖callback回帰試験を追加。
  **異常終了／SQL応答消失のQ01と永続pendingの安全な回復契約は未解決**。
- **R03 旧世代DELETE失敗**：
  新世代のREADY公開は維持しつつ、削除失敗をerror_logに記録。
  READY行の`failure_count>0` と`retry_after`を「旧世代掃除待ち」として使用し、
  Cron/手動/CLIの次回バッチで再試行する。DELETE復旧後にフラグを解除。
  正常なready添付を毎回再構築する方式には戻さない。
  複数回のDELETE失敗と復旧のMySQL回帰試験を追加。

**CI判定は各変更コミットの結果を参照し、PR #66がDraftの間はPR #65へ
マージしない。** #43の自動切替条件とQ01は独立したブロッカー。

## 2026-10-29 by-mid更新の追加レビューへの対応（PR #66のみ）

- **新R01／High：サニタイズ後の予約漏れ**
  `update_metadata_by_mid('post',...)` は `update_post_metadata_by_mid` の
  prefilterを通過した後で `sanitize_meta()` を呼ぶ。
  by-mid専用の事前ガードはdirty+pendingの確保に限り、
  予約はCoreがサニタイズと直列化を終えた **`update_postmeta` action
  （DB UPDATE直前）** で実行する。サニタイズの二重実行はしない。
  保存対象が未予約なら `invalidate_global()` をSQLで確定して認可を
  fail-closedにする。全体失効もできなければ例外でDB UPDATEを阻止する。
  Apache上の匿名HTTP回帰試験で、公開Aのファイルパスに保護Bの
  `_wp_attached_file` と `_wp_attachment_metadata` が
  サニタイズ後衝突する両ケースを検査し、再構築前503、復旧後200を確認する。
- **新R02／Medium：非添付投稿への誤適用**
  `guard_by_mid()` と `guard_delete_by_mid()` の両方で
  `get_post_type($post_id) === 'attachment'` を必要条件とする。
  実WordPressの通常投稿で両メタキーのby-mid更新・削除を行い、
  状態行・全体audit epoch・READY・公開画像認可が不変であることを検査する。
- **新R03：遅いPHP shutdown callback**
  直前のレビュー対応による動的finalizerを維持。
  実WordPress／Apacheで通常終了時の回収・再構築・配信復旧を再検証する。
  プロセス異常終了・SQL応答喪失のQ01は**引き続き未解決**。

なお`update_postmeta`はactionであり、戻り値でDB UPDATEを中止できない。
そのため、予約失敗時に**全体失効または例外による書込み中断**のいずれかを
必須とする。この失効は厳格モードでも全体配信を一時停止し得るため、
運用監視と回復手順が必要。

## 2026-10-29追加レビュー：非標準移動と旧世代掃除の最小化

- 異ディレクトリ移動の中間状態は特殊な派生ファイル予約をせず、
  上記の全体失効・dirty・通常Cronに委ねる。操作の禁止ではなく、
  メタデータ整合性と通常の再索引ができるかを試験する。
  公開Aが新ディレクトリの派生パスを持っていても、異常検出後の
  匿名公開を認めない。データ不整合を解消できない場合はユーザーが修正する。
- READY旧世代削除の再試行は `retry_after>0` の正の時刻を持つものだけ
  を選ぶ。正常なREADY大量行（`retry_after=0`）を走査候補から除外する。
  MySQLの実行計画と大量行数での独立した負荷計測は別途実施する。
- この簡素化で、PHP異常終了・SQL応答消失のQ01、管理外ファイルのIssue #43
  が解決したと主張しない。PR #65/mainは変更しない。

## 2026-10-29追加レビュー：計数負荷、DB間ロック、掃除失敗時の復旧

- **R01／Medium：進捗表示のDB負荷**：認可に必要なREADY・カーソル等は
  都度SQL制御行から取得する一方、`COUNT(*)`による件数集計は
  15秒の短期transientに保存し、AJAXや管理画面で毎回実行しない。
  CLIの各バッチは`build_status(false)`で軽い状態判定のみ行い、
  件数の表示は20バッチに1度に減らす。集計は近似の進捗表示用であり
  認可・安全判定には利用しない。実WordPressで連続ポーリング時に
  COUNTが再実行されないことを検証。
- **R02／Medium：MySQLロック名前空間**：`GET_LOCK()`はMySQLサーバー単位のため、
  接続先DB名（`$wpdb->dbname`、利用できなければ`SELECT DATABASE()`）、
  テーブルprefix、必要なら添付IDをハッシュ化してscan/添付単位の
  両ロック名を生成する。別DB・同prefixの2接続で独立性を実測。
  DB名が取得できない場合は処理を中断し、既知の共有ロックにフォールバックしない。
- **R03／Medium：DELETEと再試行記録の両方が失敗**：個々のREADY監査で
  既存`attachment_id`索引を利用してactiveと旧世代の行を同時に読み、
  世代不一致を検出する。正本・active世代・前後revisionが一致する時のみ
  旧世代を`cleanup_obsolete_generations()`で再回収する。
  正常READY添付の世代やファイル行は書き換えない。
  DELETEとretryフラグの二重失敗を注入し、次の通常監査で自動回収する試験を追加。
- **Q01／P0（別途要解決）**：pendingのUPDATEがDB側で成功したのに応答が
  失われるケースは、非一意なcountの再減算では安全に回復できない。
  耐障害的なmutation IDと冪等な消費記録などの独立設計・競合試験が必要。
  今回の小規模改修で解決したとは扱わない。
