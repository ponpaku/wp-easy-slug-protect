# #67: 自動復旧と可用性を含むメディア索引の設計判断（2026-11-02）

> **状態：設計検証済みの候補と、未解決条件の境界を明示する技術判断。製品導入済みではない。**  
> 対象：`ponpaku/wp-easy-slug-protect`、Draft PR #77（**検証用**）。PR #62／main／本番DBスキーマは未変更。

## 要求（正確性だけでなく稼働継続）

- R1: 保護所有者を見落とす匿名HTTP200を絶対に「正常」とみなさない。
- R2: 普通のPHPの正常終了／異常終了による更新チケット残留が、無期限503を起こす設計は不採用。
- R3: 更新ごとに全サイトのメディアを停止せず、できる限り添付単位に影響を限定。
- R4: MySQL SQL再送による二重増減算を排除。
- R5: 現行のメディア用2テーブルを維持し、可能なら`state`追加1列だけで実現。
- R6: WordPressの通常SQL/APIや他プラグインとの互換性を優先。全件SQL書換え・wp_* DBトリガーは副作用の検証なしに採用しない。
- R7: 想定外の実行基盤では、まず対応不能を検出して誤ったstrict保証を有効化しない。

## 新たな実験結果：安全な自動GCのための根拠

### 危険：タイムアウト／MySQL接続ロック消失だけでチケットを回収

[Actions #41411625109](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41411625109) （8/8成功）。

実WordPressの`update_post_metadata`フィルター内でPHPを停止する。更新IDと候補パスは独立COMMIT済み。PHPが生きているのに、そのプロセスの**独立MySQL livenessセッションだけ**をKILLする。別接続からGET_LOCKを取得できてしまうため、誤ったreaperは更新IDを削除し、古い正本からREADYへ再構築する。PHPを再開するとWordPress Coreは正本を変更。新しい保護所有者の索引が欠落し、匿名HTTPは200で実際のJPEGを配信した。

**結論**：単なるTTL、DB接続ID、GET_LOCKだけで自動解放する設計は不採用。「生存が観測されない」は「将来の書込みが不可能」と同義ではない。

### 有望：PHPプロセス期間のPOSIXファイルロック

[Actions #41412148967](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41412148967) （8/8成功）。
`tests/wordpress-issue-67-flock-auto-recovery-ci.php`：

- すべての書込み側が同一添付の**永続ロックファイル**で`flock(LOCK_SH)`をWordPress APIの正本書込み以前に取得し、**PHP実行終了まで保持**。
- reaperは同じファイルの`flock(LOCK_EX|LOCK_NB)`を取得できたときのみチケットを回収。
- PHP生存中は回収保留・匿名HTTP503。
- PHPを実際に`SIGKILL`すると、OSがロックを解放し、**自動GC→正本再構築→元の公開200**。
- 独立MySQL liveness接続だけをKILLしてもPHPのファイルロックは残り、回収保留。WordPressが正本更新を完了してPHPが終了した後は**自動GC→所有者競合403**。

**これにより「PHPクラッシュ＝永久に管理者手動復旧」とはしなくて済む、単一サーバー向けの実用案が得られた。**

### 落とし穴1：ロックファイルの再作成

[Actions #41413017428](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41413017428)（8/8成功）。
PHPが古いinodeのLOCK_SHを保持していても、ファイル名をunlinkして再作成すると、reaperは新inodeのLOCK_EXを取得できる。**ファイル名だけでは安全ではない**。

設計条件：ロックファイルは絶対に通常削除しない。ロック対象の`st_dev/st_ino`とランダムなロックファイル生成世代を更新ID登録時にstateの1列JSONへ記録し、回収時にすべて照合する。異なる場合は自動回収を禁止する。権限を制限した専用ディレクトリを使う。ファイル移動・復元・サイト移行時は世代を再調整する専用運用が必要。

### 落とし穴2：PHP終了時にMySQL側のSQLがまだ終わっていない

[Actions #41412763232](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41412763232)（8/8成功）。
実MySQLのUPDATE文にサーバー側のSLEEPを挿入し、SQL実行中のPHPを`SIGKILL`。PHP OSロックは既に解放されていたが、別接続の単純SELECTでは値0。その後、**対象行の`SELECT ... FOR UPDATE`は約4.6秒待ち、値1（SQLの事後COMMIT）を観測**。

**従って`flock`単体による自動GCも不採用。** PHPの死亡を確認したあと、MySQLの実行中トランザクションを直列化する必要がある。

単一ホスト候補のreaperは、`flock(LOCK_EX)`保持中に、同じInnoDBトランザクションで**state行→wp_posts対象行→wp_postmeta対象行**を`SELECT ... FOR UPDATE`する。ロック待ちタイムアウト時はチケットを保持して次回再試行する。完了した確定正本を確認してから更新IDを削除し、索引を再構築する。実テストコードはこのロック順に変更済み。

**重要な境界**：キューに入ったSQLがまだ対象のInnoDB行ロックを取得していない場合、PHP終了・再接続だけではそれを無条件に識別できない。全Core再接続経路の厳密な保証には、下記「DB実行時のフェンシング」または同等の直列化が必要。現時点のfilelock方式を全状況での数学的保証と呼んではいけない。

### DB実行時のフェンシング（分散構成の候補・要互換性検証）

[Actions #41413844313](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41413844313) のMySQL8／MariaDB10.11統合ジョブ：実際の正本UPDATEに`state`をJOINして更新IDの存在を条件化すると、

1. 正本SQL実行中、更新ID解除UPDATEはstate行ロック待ちでブロック。
2. 正本SQLが完了してチケットを解除した後、同じSQLが遅れて実行されても**0行更新**。

これはPHPプロセス停止の有無に依存しない**DB側の認可フェンス**として有望。

ただし、WordPressは`wpdb::query()`内で接続を復旧したとき、すでに組み立てたSQLを再実行する。WP APIのINSERT/UPDATE/DELETE、by-mid、投稿種別変更・添付削除等、すべての書込みSQLにこの条件を付ける必要がある。

WordPressの`query`フィルターでのSQL書換えは技術的には可能だが、Core/他プラグインのSQL互換性・SQL形状・データを破壊する危険がある。WordPressプラグイン一般に無検証で導入してはならない。

### 単一ホスト向け暫定推奨：オペレーショナル自動回復方式

- 更新開始前に同一添付の**OS共有ロック**を取りPHPリクエスト終了まで維持。
- `state.active_mutations`には更新ID・ロック世代・開始情報を格納。件数は派生値とする。
- 独立接続で`dirty+ID+候補パス`をCOMMITし、WordPress書込み前に見えるようにする。
- Cron／CLI／例外的なメディアHTTPからの軽量なrepair要求は、ロック排他が取れたときだけ起動。持続ロック中は当該所有者の拒否を維持し、**他の所有者は配信する**。
- reaperのDBロック待ちは短い上限で退避し、`retry_after`に従って再試行。
- DB状態と正本の再監査・CAS完了後のみREADY公開。全体索引の未完了IDでも同じCASを必須条件とする。
- 定常的なPHP終了・クラッシュ後は次回Cronまたは影響メディアの最初のアクセス時に修復できる設計とする。**実運用での修復時間・負荷は未測定。**
- OSロックを共有できない環境、inodeの不一致、独立primary接続を確保できない環境はこの自動GC方式を有効化しない。**複数PHPホストで共有ファイルロックが実際に効くことを確認できない限り厳格な自動GCを保証しない**。
- 本番の認可保証は、DBでまだ実行中になり得るSQLも遮断できることを実装・検証した後に確定させる。これを無視した「短いTTLで削除」は採らない。

## 優先順位付きの製品化ゲート

| 優先度 | 判定条件 | 現状 |
| --- | --- | --- |
| P0 | PHPクラッシュ後に通常のPHP要求／Cronから自動修復できる | **単一ホストの試験で実証** |
| P0 | 生存PHPがDB切断しても誤回収しない | **単一ホストの試験で実証** |
| P0 | PHP死後のMySQL実行中SQLが再構築より遅く確定しない | **反例再現、DB行ロックによる順序対策を追加検証中** |
| P0 | ロックファイル削除・別inodeに自動回復が誤作動しない | **反例再現、世代照合は設計のみ** |
| P0 | 分散WordPressサーバーでも同等の安全性 | **未保証。環境別のモード選定が必要** |
| P0 | 全WordPress mutation hookで正本書込み・索引・チケットが同期 | **本番未実装** |
| P1 | request終了後の短時間で対象メディアを自動復旧 | **Cron/HTTPオンデマンド設計のみ。負荷未計測** |
| P1 | 通常アクセスでは高速な索引照会を維持 | **追加SQLがHTTP正常経路に不要な設計候補** |
| P1 | 複数DB、MariaDB下限、旧state移行 | **追加受入試験が必要** |

**現時点の正確な結論**：手動回復だけの設計に固定する必要はない。PHP生存期間のファイルロックと独立DBフェンスの組合せで普通のPHP異常終了から自動回復できることは証明した。しかしPHP死後のMySQL遅延COMMITも実証したため、**自動GCを安全性完成済みと宣言するのは早い**。DB書込み時のフェンシングとWordPress全APIの整合性を残課題として明示し、無条件の時間経過だけでチケットを回収しない。
