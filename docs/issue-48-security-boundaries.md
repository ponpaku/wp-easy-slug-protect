# Issue #48: 静的メディア配信と起動ゲートの保証境界

対象: PR #49。確認対象は現行 `main` のApache/LiteSpeed/Nginx用Rewrite設定と、PR #49の保護状態ゲート。

## PHPのFail-closedで保証できること／できないこと

- PHP/WordPressに到達した保護ページ、REST、メディア内部配信では、不明な認可状態で公開を拒否できる。
- Apache/LiteSpeedがuploadsの物理ファイルを **PHP起動前に直接返した場合**、WordPress側の起動ゲート・503・管理者警告は実行されない。
- サイト側でuploadsのESP `.htaccess` が削除／改ざんされ、サーバーにほかの拒否ルールが存在しない状態では、書込み権限不足で修復に失敗すると直接URLを拒否できない。**これは#49で新規導入された欠陥ではなく、ファイルをWeb公開領域に置く現在の構造上の制約**。
- `.htaccess` の文字列一致確認はApacheの `AllowOverride`、実ルール適用、他ディレクティブの影響、CDNキャッシュを保証しない。
- Nginxでは `.htaccess` が無効。PHP側から外部 `location` 設定の適用を自動保証できない。LiteSpeedの独自キャッシュ・リダイレクトにも別途構成確認が必要。
- 保護対象が物理静的URLでWeb公開される構成で、外部でRewriteを消せる管理主体（運用者／デプロイ処理／別プラグイン）が存在する限り、「**Rewrite紛失でも静的直URLを必ず遮断できる**」とは表示しない。

## 責務の境界とPR #49のマージ条件

- **ESPの責務（必須）:** 自ら管理するuploads/.htaccessを更新する際、第三者ルールを変更せず、ESPルールを不正に消さず、既存ファイルを直接上書きせず、失敗時に元ファイルを保持または復元する。変更後の照合を行う。
- **ESPの責務（必須）:** メディア保護が有効で、ルールが必要な環境では、起動時にルールの存在と内容を確認し、設置できない場合はエラーを通知する。正しいルールがWebサーバーで実際に働くことを実HTTPで確認する。
- **環境の責務（#49の追加実装対象外）:** 運用者／外部アプリがESPの管理外で.htaccessを削除・変更した場合や、ApacheのAllowOverrideが無効化された場合にも自動的に絶対防御すること。独立のOS権限／Webサーバー設定で対応する領域であり、#49のマージ阻止要件にはしない。
- **障害境界:** ESPは既存ファイルの置換前に退避を作り、置換後検証に失敗した場合に復旧を試みる。電源断・媒体故障・外部プロセスの割込みがあれば自動復旧は無条件には保証できず、失敗を成功と扱わず管理者が復旧できるようにする。

## WordPress・ESP・運用環境の障害時の責任分界（R02の設計原則）

> **設計判断と実装の状態（2026-10-15）。** PR #49のDraftでは、`ESP_Protection_State::register_failure_hooks()` を「保護設定が不明なら広範囲拒否」「保護設定を取得できるなら経路に応じた拒否」へ変更した。保護パスありの集約表示・匿名REST等は認可フック不在中の漏洩防止のため拒否する。**実WordPressのHTTP・REST検証は未完了であり、全経路の安全性を保証する記述ではない。**

| 発生元・状態 | ESPが責任を負う範囲 | ESPが引き受けないこと |
| --- | --- | --- |
| **WordPress本体・DB基盤自体の障害** | WPが正常にフックを実行でき、ESPの認可に必要な情報だけが取得できない場合は、該当する認可判定を安易に許可しない | WP本体のエラーハンドリングを独自503・復旧処理で置き換えること、WP/DB全体を修復すること |
| **ESPの更新・移行検証失敗、検証待ち・排他競合** | 状態と失敗理由を診断できるようにし、保護の判定を要する処理を安全に扱う | 状態が `PENDING` / `FAILED` 等である**という理由だけ**で、無関係な公開ページ・REST・AJAXまで一律503にすること |
| **ESPの設定・認可キャッシュ・認証用テーブルの不整合** | 保護対象の不正公開を防ぎ、特定できる保護経路で認可失敗を拒否する | WordPress全体の提供可否をESPが決めること。認可に無関係な機能へ障害を波及させること |
| **ESP管理下のRewrite更新失敗** | ESPブロックの安全な保持・復元、失敗の通知、必要な新規保護操作の抑止 | PHPの503でWebサーバーの静的直配信問題まで解決したかのように扱うこと |
| **Apache/Nginx・CDN・別プラグイン・運用者の変更** | 対応範囲と検証不能な条件を明示する | 外部設定の修復や他プラグインの配信ポリシーの代行 |

**判断規則：** 「検証に失敗した」「保護対象がある」「保護範囲を確定できない」は異なる状態。**確実に公開可能な経路は、ESPの異常だけで止めない。** 一方で、保護の可能性が残る経路を無検証で公開してよいとはしない。検索・一覧・フィード・RESTは保護情報を含み得るため、URLだけを見て安全な公開ページと断定しない。

**未決事項（R02）：** 設定全体が読めず保護範囲をまったく特定できない場合の、経路ごとの拒否範囲と復旧方法は別途詰める。WordPress標準のエラー対応を重複実装しないこと、および新しい汎用認可ポリシー（#43）・Migrator（#44）をこの修正のために作らないことを前提とする。失敗原因の分類・状態の復帰は軽量に扱い、毎リクエストの重いDB検証や無制限リトライを導入しない。

## R02確定判断（起動時の過剰503を修正するための実装契約）

PR #49の `ESP_Protection_State::boot()` は非READY時に `ESP_Core` / `ESP_Filter` / `ESP_Media_Protection` の通常登録を中断する。**503フックだけ削ると保護経路が無防備になるため不可。** 起動状態と、配信してよいかの判断を分離する。

1. **原因を問わず一律503にしない。** `FAILED`、`UPDATING`、Rewrite不一致、スキーマ不一致、検証待ち等の状態名だけでは、WordPressの一般公開コンテンツまで停止する根拠にならない。WordPress/DB基盤の障害はWP自身の処理に委ね、ESP独自の全体修復・リトライを増設しない。
2. **例外：保護設定が取得不能・形式破損。** `esp_settings.path` が安全に読めず、保護対象を確定できない場合は、公開コンテンツを広範囲に拒否してよい。通常ページは適切なエラーコード付き `wp_die()`、RESTは `WP_Error` など応答方式を使い分け、復旧できる管理経路は維持する。
3. **読める設定でも保護は維持。** 既知の保護パスは認可未確認のまま通さない。投稿一覧・検索・フィード・サイトマップ・REST・メディアなど、保護情報が混入し得る経路は「無関係」と決めつけない。保護フック未登録の状態で一般公開へフォールバックする修正は禁止。確実に公開可能な部分だけを維持する。
4. **新たに保護を成立させる操作に限定した前提条件。** Rewrite設置・照合等ができない場合は新規メディア保護指定と既存保護メディアのOFF→ON切替を拒否する。通常アップロード、保護解除、管理者の明示的OFF、プラグイン無効化・アンインストールは巻き込まない。
5. **一時的検証未完了と確定不整合を区別。** DBロック競合などは破損確定の `FAILED` と同視しない。毎リクエストの重い検証や、WordPress/DB全体をESPが復旧する機構は導入しない。
6. **内部エラーを検知可能にする。** 設定取得不能・確定した検証失敗を `error_log` 等で通知する。保護URL、パスワード、トークン、SQL全文は書かない。同一異常の大量出力は避け、管理者の既存復旧画面を残す。
7. **テスト条件。** (a) path=[]/media OFFで一時・確定検証失敗しても無関係な公開ページ・RESTは利用可、(b) pathありの場合は保護URLと情報を含み得る集約経路が拒否される、(c) 設定取得不能・形状異常なら公開を広く拒否、(d) media ONのPHP配信経路は非READYで本文公開されない、(e) 管理者復旧経路を維持、(f) WP/DB障害をESPが独自に全体復旧しない。

**適用範囲：** R02の起動ゲートのみ。外部WebサーバーがPHP起動前に配信する静的ファイルの遮断保証、添付ファイル帰属判定（#42）、未知メディアの公開方針（#43）、拡張子の仕様検討（#51）、#44の本格Migratorは別件。実HTTPの網羅検証前に「全リスク解消」と記載しない。

## 管理者操作と責任範囲（PR #49の現行受入基準）

- **保護ON時の障害**と、**管理者が明示的に行うOFF・プラグイン無効化・アンインストール**を区別する。Fail-closedは後者を妨げるための権限ではない。
- メディア保護のOFFは保護メタあり・DB件数不明でも、公開リスクの確認を受けたら保存できる。メタ自体は残し、再ON時に必要なRewriteを検証する。
- プラグイン無効化時は、保護メタ件数と無関係にESP自身のRewriteブロックの安全な削除を試みる。他者のルールと内容・権限を保持する。権限/競合/不正マーカーで除去できなくても無効化を妨げず、**残存Rewriteの手動削除が必要になり得る**ことをエラーログで通知する。
- アンインストール時も既存の原子的なRewrite保全処理を使うが、除去失敗でWordPress標準の削除を止めない。ESPのDB・設定削除を続行するため、**残存ルールをプラグイン自身が自動復旧できるとは主張しない**。管理者は必要に応じてuploads/.htaccessのESPマーカーだけを手動削除する。
- 公開 `esp-media` クエリはRewriteの拡張子制限を通らないため、PHP側でも配信可能な拡張子と隠しファイル/隠しディレクトリを検査する。これは#49の入口での回帰対策であり、許可拡張子を持つ未登録ファイルの所属・公開方針そのものは#42/#43の担当。
- WebサーバーやCDNの外部ルールをESPが制御・保証しない。OFF・無効化・アンインストールで保護を失うことは管理者の明示的な選択であり、操作前に確認すべきリスクである。

## 運用上の必要条件と選択肢

1. uploads直URLでアクセス可能な対象拡張子に、認可以前の強制的なサーバー側制御があることを確認する。PHPが動くかではなく、**サーバーが静的実ファイルを直接配信できるか**を基準にする。
2. より強い保証を求める環境では、物理保護ファイルをWeb公開ディレクトリ外へ置き、認証後だけ安全な内部配信を行う方式、あるいは外部で管理する拒否優先ルールを検討する。現PRでは保存方式・サーバー設定の全面変更を行わない。
3. このPRの自動修復は `uploads/.htaccess` のESPブロックについてのベストエフォート。ルール欠落と権限障害が重なった場合、プラグイン単体で静的配信を止めることはできないため、**監視・構成管理・初回セットアップ・外部変更の防止**を運用条件とする。
4. Rewrite保護を有効にしていても、添付ファイルの所有者・派生画像の完全解決（#42/#43）、認証済み配信の共有キャッシュ（#31/#43）、CFM固有経路（#40）は別要件。ここで保証済みとしない。

## R04との関係

PR #49の認可キャッシュは、WordPressの標準postmeta APIによる保護メタ変更前に失効可否を確認し、失敗時は当該変更を拒否する。同一リクエストでは不明なキャッシュ読取りを拒否する。

これは、PHPを迂回する直接SQL更新、外部で直接transient/optionを変更するコード、新旧PHPコードの完全な並走、およびDB・キャッシュ永続層が同時に障害を起こす構成の**全条件での一貫性保証ではない**。保護メタ書換えとキャッシュ状態の実DB統合試験は引き続き必要であり、旧PHPとの互換は#44で扱う。
