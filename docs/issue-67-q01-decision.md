**決定日：2026-11-05**  
**状態：Q01は既知の未解決問題。PR #62ではDBトリガー方式を導入しない。将来の対応方式は未決定。**  
関連：[Issue #67](https://github.com/ponpaku/wp-easy-slug-protect/issues/67) / [PR #62](https://github.com/ponpaku/wp-easy-slug-protect/pull/62) / [検証用PR #77](https://github.com/ponpaku/wp-easy-slug-protect/pull/77) / [製品実装検証PR #78](https://github.com/ponpaku/wp-easy-slug-protect/pull/78)

## 1. 何が問題なのか

WordPressの添付ファイルに対する所有権・保護状態は、`wp_posts`・`wp_postmeta`が正本であり、ESPのメディア索引はそこから作る派生データである。正本を書き換えている間は対象の索引を`dirty`にし、`pending_count`（更新中の処理数）がゼロになってから再構築する。

Issue #67には、同じ`pending_count`の過剰減算に至る**別々の2経路**がある。

| 区分 | 起点 | 状態 |
| --- | --- | --- |
| **F01** | WordPress Coreが、同じキーの複数メタ行に対して1回の更新で複数の更新後フックを発火する。後フックごとに減算すると過剰減算する | **修正済み**。PR #70の修正を既存の#62系索引実装に取り込み、更新後フックの件数ではなく事前に取得したローカルチケットをリクエスト終端で完了する |
| **Q01** | DBが減算を確定した後、成功応答だけが失われ、WordPressの`wpdb`が同じ非冪等SQLを再接続後に再送する | **未解決**。F01対策では防げない |

Q01の実証例：2つの更新処理A・Bがあり`pending_count=2`のとき、Aの`pending_count=pending_count-1`がDBでは成功（2→1）する。しかし成功応答が失われ、`wpdb`による同SQL再送がもう一度成功（1→0）すると、**Bがまだ更新中なのにゼロになる**。

2026-10-29の実WordPress＋MySQL＋通信中継試験で、**`wpdb`による二重減算そのものは再現**した（[CI証拠](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/40886488076)）。ただし、実メディアの二重所有・索引再公開・匿名HTTP配信まで結んだ**情報漏えいの成立は実証していない**。発生頻度や攻撃者からの誘発可能性も未評価であり、「安全」「直ちに漏えいする」のいずれも断定しない。

Q01と別に、異常終了で`pending_count`が残り続ける可用性・復旧問題がある。時間だけで待機数をゼロに戻すことは、進行中の別処理を誤って解除するため採用しない。

## 2. このPRでQ01に対応しなかった理由

**製品判断：easy-slug-protectでは「一般的なWordPress環境で広く動くこと」を優先する。** 「easy」は画面操作だけでなく、導入、アップデート、無効化、アンインストール、障害対応、継続的な保守までを含む。

PR #77では、既存の索引2テーブルを使い、stateの更新ID列・DBトリガー・DBセッション変数・名前付きロックによってSQL再送／遅延SQLを検知する構成を検証した。PR #78では同方式を製品コードに組み込み、MySQL、MariaDB、WordPress、ApacheなどのCIを成功させた。**技術的な成立性を確認したことと、ESPの標準方式として採用することは別の判断である。**

#78の方式を**標準実装として採用しない**理由は次のとおり。

1. **環境依存の増加**：WordPress Coreの`wp_posts`・`wp_postmeta`にDBトリガーを設置し、作成権限、InnoDBのトランザクション原子性、DBの対応機能、DB接続／名前付きロックに依存する。一般的なホスティング環境の組合せを制限する。
2. **WordPress本体への影響**：プラグインを無効化してもトリガーはDBに残る。設置・更新・削除の失敗は、プラグイン内部だけでなくCoreの添付情報の書込みにも影響し得る。
3. **障害の影響範囲**：追跡不能な変更では全体索引を`DIRTY`にする方式のため、無関係なメディアの配信まで停止し、全件再監査に時間がかかる可能性がある。
4. **運用・保守コスト**：DB権限、ストレージエンジン、他プラグインのトリガーとの共存、再接続、クラッシュ回収、デッドロック、移行・アンインストールまで継続的な互換性検証が必要となる。まれと推定されるQ01への対策として、現時点では製品負担が大きい。

これは「R01～R03さえ直せば採用する」という判断でも、「DBトリガーの技術が誤り」という判断でもない。**必要な保証のために負う標準環境の制約が、汎用WordPressプラグインの優先方針に見合わない**ためである。Q01が軽微・無害と証明されたから見送ったわけではない。

## 3. PR #62に適用する境界と現状

- **取り込むもの**：現行のWordPressフックによる事前`dirty`化・対象パスの保護、F01のリクエスト単位の完了整理、既存索引の監査・fail-closed処理。これらは#62の既存コード・設計の範囲。
- **取り込まないもの**：#78のCore DBトリガー6本、`active_mutation_ids`を前提にしたschema v4、DBセッションactor、DBトリガーに結び付く更新ID／回収の仕組み、旧表名を変更する#78固有の移行。
- **残る限界**：Q01のACK消失／再送による非冪等カウンター操作は未解決。WordPressフック外の直接SQL、PHP終了後の遅延SQL、FTP/CDNなども、#78と同等の検知保証は主張しない。
- **既存の運用制約**：索引strictモードは自動で有効化せず、[Issue #43の保護範囲・移行方針](issue-43-media-scope-policy.md)を優先する。strictを有効にしても、既知のQ01が解決したとは解釈しない。互換モードの未登録ファイル公開リスクも別途存在する。

**PR #62をマージすることは、Issue #67を解決済みとすることや、あらゆるDB障害での誤公開防止を保証することを意味しない。** 個別の受入判断では既知リスクを明示して扱う。#77/#78は調査記録として参照するが、コードは#62に統合しない。

## 4. 将来再検討する場合の判断基準

方式はまだ選定しない。まず、一般的なWordPress環境での導入容易性を保てる候補を比較する。

- **必要な安全性**：同じ更新開始・完了SQLが2回実行されても、別ワーカーの進行中状態を消さない。WordPress正本より古い情報を安全と誤認しない。
- **実装の優先順位**：WordPress標準API／フックと既存の索引の利用を優先し、必要であれば更新単位の冪等性や条件付きCASを評価する。新しいテーブル／DBトリガーを既定の解決策にしない。
- **検証の必須条件**：実`wpdb`のACK消失・再送、2ワーカー並行更新、複数メタ行、異常終了後の復旧、監査とHTTP配信の競合を分けて検証する。安全性と可用性、環境互換性、保守負担を比較する。
- **保証できない範囲の明示**：DBトリガーなしでは、フックを迂回したSQLや失効後の遅延SQLを同等に検知できない可能性がある。保証を拡大したと主張する場合は別途実証する。
- **判断の再開条件**：Q01による実際の被害経路、発生頻度、利用環境、実現可能な最小対策の比較が明らかになった段階で、残存リスク受容も含め改めて製品判断する。
