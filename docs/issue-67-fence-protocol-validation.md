# Issue #67 — 更新フェンス再設計の実WordPress検証（2026-11-02）

> **調査・検証記録。製品実装の承認ではない。**
>
> 検証専用 [PR #77](https://github.com/ponpaku/wp-easy-slug-protect/pull/77) は
> PR #62 の未マージブランチから分岐。本体認可クラスと本番用DB定義は未変更。
> 最終検証：[Actions #41368674214](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41368674214)（7/7成功）。
> WordPress 7.1.3、PHP 8.3、MySQL 8.0.46、独立PHP/MySQL接続、Apache匿名HTTP。

## 不変条件 — 何が成立したら不合格か

I1. WordPress正本の変更が確定する前に、新たな保護所有者候補を認可索引から
    見落とさないこと。索引にない所有者は単一SQLでJOINしても検出できない。
I2. 書込みの**可能性が残る処理**がある限り、該当パスをREADYな公開所有者だけに
    基づいて匿名配信しないこと（必要なら全体READYを取り消す）。
I3. SQLがコミットした後のOK応答消失、wpdbの同一SQL再実行、
    重複WordPress後フックでも、別ワーカーの未完了更新を消費しないこと。
I4. フェンス登録がROLLBACK／再接続で消え、正本の書込みだけが別接続で
    COMMITされることを許さないこと。
I5. 未完了更新IDの解除を推測で行わない。障害時は認可拒否のままとし、
    書込み処理が確実に終了した証拠がある場合にだけ復旧すること。
I6. 通常の匿名HTTP検索に追加のDB往復を入れないこと。PHP配信の性能を実測する。

## 確認済み：既存方式の失敗

### 事前フックのフェンスと候補パス予約の両方が失われる

1. 公開添付Aが `esp31-public-150x150.jpg` を持つ。
2. 保護済み添付B（`path_http`）が同じパスを派生ファイルとして追加する。
3. 外部`START TRANSACTION`中、ESP事前フックはBをdirty化し、Bの候補ファイル行を
   **未コミット**でステージする。
4. Coreの正本`wp_postmeta`更新前にDBセッションを`KILL CONNECTION`する。
   旧トランザクションの失効・候補はROLLBACK。Coreは接続を復旧し、
   **正本だけを更新・確定**する。
5. 対象PHPワーカーの終了処理前に、独立Apacheで公開パスへ匿名HTTP GET。

**実測**：Bの正本メタに新しい保護対象パスが存在する一方、Bの索引候補0行、
Bの状態`ready,pending=0`、`resolve()`はAの公開所有者だけを認識。
**匿名HTTP 200、返却バイト列とディスク上のJPEGが完全一致**。

ログ：`ESP67_COLLISION_STATE`、`ESP67_COLLISION_HTTP vulnerable 200`、
`ESP67_REAL_WP_PUBLIC_BYPASS`。

このJPEGはもともと公開済みの検証用画像であり、非公開だった秘匿データの
流出を実証したとは言わない。しかしstrictの「複数所有者なら拒否」という
認可不変条件は実際のHTTPで破綻した。故障注入下の再現であり、
実サイトでの頻度・攻撃者による誘発可否は未測定。

### 保護IDのLIVE JOINは十分でない

現行`ESP_Media_Index::resolve()`は、ファイル索引に**存在する**所有者の保護IDを
WordPress正本と照合する。新しい保護所有者の索引行が存在しなければ、
元から索引済みの公開所有者の照合だけは成功する。

## 確認済み：2つの部分対策

### 更新ID集合＋revision CAS

`state`を模した実MySQL試験と、実WordPress `wpdb`＋TCP中継による
SQL ACK消失・Core再送で、`["A","B"] → ["B"]`のCAS解除が
再送されてもBが消えず、revisionが1回だけ進むことを確認した。
実stateへの一時列追加・独立2ワーカーWordPressフック・
実HTTP503／両者完了後302も確認。

**制約：** これだけでは外部トランザクションがROLLBACKされると
登録した更新IDも消える。既存のpending_countと併走する試験であり、
製品コードを全置換した検証ではない。

### 独立DB接続で「正本変更前」に永続フェンス＋候補予約

同じ衝突シナリオで、WordPressの本来の事前ガードより**先に**、
独立したMySQL接続の1トランザクションで、
Bの`state`を`dirty,pending_count=1`にし、
B→公開パスの候補`files`行を挿入・COMMIT。

その後、**元の外部トランザクションを強制切断**し、
Coreが正本を再接続先で確定しても、独立したフェンスは残った。

**実測**：Bの状態`dirty,pending=1`、候補行1件、
`resolve()`は`error`、独立Apache匿名HTTPは**503（本文非配信）**。
復旧操作後は元の公開画像HTTP200に戻った。

これは**既存の数値pendingと試験用priority-3ガード**による
原理実証であり、本番に必要な更新ID集合と結合済みの実装ではない。
初期の失敗試験では前のフェーズの同期マーカーを誤認したため、
最新Runでは各フェーズ開始前にマーカーを削除して再検証済み。

## 推奨する設計候補（未実装）

1. 新テーブルは作らず、既存`esp_media_file_state_v1`へ
   `active_mutations`（bounded set of random IDs）を追加する。
   `pending_count`は集合数から導出するのみとし、`+=1`／`-=1`を廃止。
2. WordPressの正本書込みを許可する**前**に、
   独立したDB接続で更新ID登録＋添付dirty化＋新しい所有パス候補予約を
   **同一InnoDBトランザクションで確定**する。
   成功応答消失時は同じIDを使って再読込・確認する。
   完全な予約を確認できない場合は書込みを拒否する。
3. 正本書込みが呼出元トランザクション内でも、保留IDを早期に消さない。
   例：元の`wpdb`接続がstate行に確実な行ロックを保持できるなら、
   独立接続からの完了処理は元のCOMMIT/ROLLBACKまで待たされる。
   ただし元の接続が切断され、Coreが再送する場合も再検証が必要。
4. WordPressの複数メタ行後フックを更新単位の完了と同一視しない。
   PR #70のリクエスト内重複排除を残し、各更新IDは1回だけ解除する。
5. 予期しないDB切断、未確定のWordPress書込み、異常終了、ID集合破損、
   ID数上限超過では、**解除・READY化を行わない**。
   自動タイムアウト解除は禁止。復旧には書込みの停止と再監査を要する。
6. strict時に新しい所有パスの正確な予約ができない場合は、**独立して
   COMMITした全体coverage失効**を使うか、更新自体を拒否する。
   後者を優先すると通常サイト全体の503を減らせる。

## 方式比較・トレードオフ

| 方式 | SQL再送 | 外部TX再接続 | 認可コスト | 実装/運用リスク |
| --- | --- | --- | --- | --- |
| 数値pendingのみ（現行） | × 二重加減算 | × フェンス消失を再現 | 既存通り | strictでは不合格 |
| 同一接続の更新ID集合＋CAS | ○ 二重加減算 | × フェンスはTXで消える | 既存通り | 1列だけでは不合格 |
| **独立コミットされたフェンス＋候補予約＋更新ID集合** | ○ 見込み・CAS部分実証 | **○ この故障条件でHTTP503を実証** | HTTP照会追加なし | 更新時の追加接続/ロック順序/復旧が課題 |
| WordPress正本の全件照合を毎HTTPで実施 | 完全性検査可能性 | 状況による | 非常に重い | メタ値検索と所有者列挙の上限が難しい |
| DBトリガーで正本変更と全体失効を原子的に連動 | 原理上可能 | 原理上可能 | HTTP照会追加なし | TRIGGER権限、Core表改変、毎回全件監査。未実証 |

**追加の問題：** 独立接続方式は、呼出元のトランザクションがすでに
state行をロックしていると先行フェンスを確定できない。
実MySQLで別接続の行更新がロック待ちタイムアウトすることを確認。
したがって「先行コミットが成功した場合だけ書込み許可」という
**fail-closed契約**と一貫したロック順序が必須。

## 次の本番実装前の受け入れ試験

- 更新ID登録／解除の実`wpdb` ACK消失、独立2ワーカー、メタ重複、no-op、by-mid、
  添付追加／削除／投稿種別変換、候補パス変更・所有者競合。
- 正本SQLを発行する前の任意位置でのDB切断、外部TX COMMIT／ROLLBACK、
  完了処理のロック待ち／DB再接続／遅延PHP shutdown。
- 異常終了して残った更新IDの復旧フロー。ワーカー停止を確認できない場合、
  自動的な削除・READY化は禁止。
- MySQL/MariaDBのサポート下限、独立接続権限・最大接続数、ロック順序、
  更新時の負荷、スキーマ移行、既存pending値の扱い。
- strict匿名HTTPは常に必要な所有者がすべて反映されるまで503/403とし、
  保護画像の生本文が未認証に配信されないこと。

**結論：** 新テーブル不要の設計は有力。しかし、
`state`への1列追加だけでは不足し、
**外部トランザクションのROLLBACKで消えない「正本書込み前の永続フェンス」**と、
**安全な更新完了・復旧プロトコル**が必要。


## 2026-11-02 追加：更新ID集合＋先行永続フェンス＋caller行ロックの一体化実証

**実行**：[GitHub Actions #41370951448](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41370951448) **全7ジョブ成功**。
初期一体化版：[Actions #41370542704](https://github.com/ponpaku/wp-easy-slug-protect/actions/runs/41370542704) 全7ジョブ成功。
コード：\`tests/wordpress-issue-67-integrated-fence-ci.php\`、\`.github/scripts/test-wordpress-apache-http.sh\`。

### 何を組み合わせたか

1. 実際の\`esp_media_file_state_v1\`に試験用\`esp67_mutation_ids LONGTEXT\`を1列一時追加。
2. 実WordPressの\`update_post_metadata\`に試験専用priority 3 guardを設定。
   **このPHPプロセスでのみ**既存ESPのpriority 5 metadata guardと
   \`updated_post_meta\` actionを外し、従来pending_countとの二重管理を避けた。
3. guardは独立したmysqli/InnoDBトランザクションで
   \`state.status=dirty\`、更新ID集合、\`pending_count=count(IDs)\`、
   新規所有者の候補\`files\`行をまとめてCOMMIT。登録呼出し2回でも同一IDに収束。
4. **独立コミット後に、元の\`wpdb\`接続が\`SELECT ... FOR UPDATE\`で
   同一state行をロック**。呼出元が外部トランザクション内なら
   そのCOMMIT/ROLLBACK/接続消失まで別接続の完了処理は進まない。
5. 正本書込みの終了後に独立mysqliで自分の更新IDだけを解除し、
   その後Cron相当の\`reindex_attachment()\`がWordPress正本から索引を再構築。
   更新IDが残る限りREADY公開しない。

### 実WordPressでの合否

| ケース | 実測と判定 |
|---|---|
| 外部TX中、正本が未コミットのまま独立接続で更新IDを解除 | **ロック待ちタイムアウトで解除拒否**（PASS） |
| 外部TXをROLLBACK | 先行コミットの更新ID/dirtyは残留。ROLLBACKされた正本を前提に、TX終了後だけ解除・安全に再構築（PASS） |
| 外部TXをCOMMIT | COMMITまでは解除拒否。正本と独立フェンスが併存し、COMMIT後に解除・再構築。保護/公開の2所有者競合は\`ambiguous\`として拒否（PASS） |
| ESP事前ガード後、WordPressの元DBセッションを\`KILL CONNECTION\` | Coreが正本のみ再送・確定しても、独立確定したID＋候補行は消失せず（PASS） |
| 更新ID保留中の独立匿名Apache HTTP | **503・画像本文非配信**（PASS） |
| 最終ID解除後・再構築した所有者競合の匿名HTTP | **403・画像本文非配信**（PASS） |
| WordPress保護メタを元に戻し再構築 | **200・公開所有者の正常復旧**（PASS） |
| 同じ更新IDの登録2回・解除2回 | 追加IDなし／他者のIDに影響なし（PASS） |
| PHPワーカー消失を模し、登録後に別PHPプロセスから状態検査 | 更新IDは残り、CronはREADY拒否、匿名HTTP503（PASS） |
| 試験ランナーがワーカー終了・未書込みを知る状態で明示回収 | 解除→正本監査→公開HTTP200（PASS）。**本番で一般的に終了を証明する仕組みではない** |

### 採否に関する重要な制限

- **本番実装ではない**：既存のmetadata guardを試験PHPプロセスで差し替えた。
  他のWordPressフック経路を本体に実装したものではない。
- **単一のWordPress API更新経路**で、公開A/保護Bの同一ファイル所有を競合させて検証。
  新規添付、by-midサニタイズ、添付削除、post_type変換、
  無関係なプラグインの直接SQL書込みは別途検証・ガードが必要。
- **後続のトランザクション制御が重要**：外部TXがstate行ロックを既に保持している、
  または元の接続がロックを失った場合は、先行フェンスのCOMMITが不可能・
  局所的な行ロックの継続性が失われることがある。そこで成功の確認まで
  WordPress書込みを拒否し、独立IDを保留してfail-closedする必要がある。
- **自動的な「タイムアウト解除」は禁止**：PHP処理が停止したまま再開する可能性がある。
  更新IDの残留を検出し、対象書込み停止・再監査を行う運用フローが必要。
- **単一のprimary DBへの独立接続**とCOMMIT可視性を前提とした試験。
  ホスティングのDB接続方式、プロキシ・レプリカ、MariaDBの下限、
  独立接続の最大数・接続失敗時のフェールクローズ、デッドロック解消、
  更新ID集合の件数・サイズ上限、スキーマ移行、性能は未検証。
- **更新IDは試験固定文字列**。本番ではランダムな高エントロピーID、
  リクエスト内の生存区間・重複フック処理、ID再利用禁止を規定する。
- \`wpdb\`の通常メタフック以外にCoreが書込みを行う場合、候補パスを
  完全に予約できないなら、**独立してCOMMITしたglobal coverage失効**か
  API更新の拒否が必要。
- 事故対応の判断では、「他者の公開所有者しか索引にいないのに正本で
  保護所有者が生えている」状態をP0の認可不整合として扱う。

**現時点の判断**：既存2テーブル＋state追加1列という構成で
必要な防護の主要部分が実現できることを実験的に支持する。
ただし本番コードへ広げる前に、全WordPress書込み経路のフェンス処理、
更新IDライフサイクルと外部TXの解除契約、障害復旧、MariaDB互換、
性能・接続数を実証しなければならない。Issue #67はOpenのまま。
